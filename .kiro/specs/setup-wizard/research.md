# Research & Design Decisions: setup-wizard

## Summary
- **Feature**: `setup-wizard`
- **Discovery Scope**: Extension (integration-focused) — adds one CLI subcommand, one bash
  script, one generated doc, and expands two existing files. No schema, adapter, MCP, or
  web changes.
- **Key Findings**:
  - The khipu router (`src/khipu.ts`) already dispatches operational subcommands through an
    `OPERATIONAL_SCRIPTS` map that spawns a `.ts` file via `tsx`. `setup-claude` and
    `setup-sync` are both thin TS scripts that shell out to OS-level work. Adding a
    `setup-env.ts` wrapper to this map is the least-invasive way to expose `khipu setup-env`.
  - The authoritative single-account variable set is pinned in `src/account-registry.ts`
    (`LEGACY_ENV_VARS`) and the security vars in steering `tech.md`. This is the exact list the
    wizard must recognise: Telegram (`TELEGRAM_API_ID/API_HASH/PHONE_NUMBER`), Discord
    (`DISCORD_TOKEN`), Slack (`SLACK_USER_TOKEN`), Email (`EMAIL_IMAP_HOST/USER/PASS`), Beeper
    (`BEEPER_ACCESS_TOKEN`), plus optional `DB_KEY`, `WEB_USER`, `WEB_PASS`, `MCP_SECRET`.
  - `TELEGRAM_SESSION_STRING` is written automatically by `config.ts#saveSessionString` at first
    Telegram login. It must be documented but never prompted.
  - macOS default `/bin/bash` is 3.2 — no associative arrays, no `mapfile`. A single-source
    variable table must therefore be a newline/pipe-delimited record set parsed with
    `while IFS='|' read`, not an associative array.

## Research Log

### Token acquisition click-paths (verified 2026-08-01)
- **Context**: Every prompt must show a precise URL + click-path + field-to-copy, verified
  reachable/current at authoring time.
- **Sources Consulted**:
  - Telegram: https://core.telegram.org/api/obtaining_api_id and https://my.telegram.org/apps
  - Discord: https://discord.com/developers/applications
  - Slack: https://docs.slack.dev/authentication/tokens/ and https://api.slack.com/apps
  - Beeper: https://developers.beeper.com/desktop-api/auth
  - Gmail IMAP: https://developers.google.com/workspace/gmail/imap/imap-smtp and
    https://myaccount.google.com/apppasswords
- **Findings**:
  - Telegram: log in at `my.telegram.org` with phone (E.164, e.g. `+14155552671`) + code sent
    in-app => "API development tools" => copy `App api_id` and `App api_hash`.
  - Discord: `discord.com/developers/applications` => New Application => Bot => Reset Token =>
    Copy. Message Content Intent must be enabled if the bot reads message text.
  - Slack: `api.slack.com/apps` => Create New App => From scratch => OAuth & Permissions => add
    User Token Scopes (`channels:history`, `groups:history`, `im:history`, `mpim:history`,
    `users:read`, plus the matching `:read` scopes) => Install to Workspace => copy the
    `xoxp-` User OAuth Token.
  - Beeper: **Settings > Integrations > "+" next to Approved connections** (not a "Developer"
    section; the older "Developers > API Access Token" wording is outdated). Token backs Signal
    and Facebook Messenger. Local API base `http://localhost:23373`.
  - Gmail IMAP: host `imap.gmail.com`, port 993 SSL; requires a 16-char App Password created at
    `myaccount.google.com/apppasswords` after enabling 2-Step Verification (normal password will
    not work).
- **Implications**: These strings are the `url`/`click_path`/`example` columns of the variable
  table. Because they are the single source of truth, correcting a click-path in the table
  automatically corrects both the prompt and the generated doc.

### CLI routing seam
- **Context**: How to expose `khipu setup-env` alongside `setup-claude`/`setup-sync`.
- **Findings**: `resolveCommand` is a pure resolver returning `{kind:'run', script, args}`;
  `spawnScript` always launches `process.execPath tsx <script>`. Introducing a bash interpreter
  branch would require widening `CommandResolution`. A thin `src/setup-env.ts` that spawns
  `/bin/bash scripts/setup-env.sh` keeps the resolver and `spawnScript` untouched and mirrors the
  existing operational scripts exactly.
- **Implications**: One new entry in `OPERATIONAL_SCRIPTS`, one new USAGE line, no changes to the
  resolver contract or `spawnScript`.

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| Bash-only + TS wrapper (chosen) | All logic + table in `scripts/setup-env.sh`; `src/setup-env.ts` just spawns bash | Dependency-free; single source of truth; matches existing bash/tsx tooling; docs generated by same script | Bash 3.2 record parsing is verbose | Table embedded as pipe-delimited records emitted by one function |
| TS-driven wizard | Prompt engine in TypeScript, no bash | Easier string handling, testable in Vitest | Contradicts brief's POSIX-bash constraint; heavier | Rejected |
| External table file + two parsers | `scripts/setup-env.table` read by both script and a docs generator | Clean data/logic split | Two consumers can still skew formatting; extra moving part | Rejected in favor of one script owning the table and emitting docs |

## Design Decisions

### Decision: Single script owns the table and emits the docs
- **Context**: Requirement 6 demands the prompts and `docs/TOKENS.md` never drift.
- **Alternatives Considered**:
  1. Embed table in bash, generate docs from a separate script — risk of skew.
  2. Embed table in bash, add an `--emit-docs` mode to the same script — one source, zero skew.
- **Selected Approach**: `scripts/setup-env.sh` defines the table once (a `var_table` function
  emitting pipe-delimited records). Default mode runs the interactive filler; `--emit-docs` mode
  renders the identical records into `docs/TOKENS.md`. The committed `docs/TOKENS.md` is a
  generated artifact.
- **Rationale**: Guarantees no drift because both consumers read the same records in the same
  process. No extra dependency, no separate parser.
- **Trade-offs**: `docs/TOKENS.md` must be regenerated (via `--emit-docs`) when the table changes;
  a test asserts the committed doc matches a fresh emit.
- **Follow-up**: Add a test that runs `--emit-docs` to a temp path and diffs against the committed
  doc so drift is caught in CI.

### Decision: Idempotent, order-preserving `.env` merge in pure bash
- **Context**: Requirement 5 forbids clobbering or reordering existing populated keys.
- **Selected Approach**: Read the target env file line by line into a temp file. For a provided
  answer whose key exists with an empty value (`^KEY=$`), rewrite that one line in place. Keys not
  present are appended at the end. Populated keys, comments, and blank lines are copied verbatim.
  Replace the original with the temp file only at the end. Values are written with `printf '%s'` to
  avoid escape interpretation.
- **Rationale**: Avoids `sed -i` portability differences between macOS and GNU; preserves order and
  formatting deterministically.
- **Trade-offs**: Slightly more verbose than `sed`, but portable and safe.
- **Follow-up**: Test with a fixture `.env` containing populated keys, empty keys, comments, and
  blank lines; assert exact preservation.

### Decision: Testability seams via env overrides
- **Context**: Tests must exercise the merge and docs emit without touching the real `.env`.
- **Selected Approach**: The script honors `SETUP_ENV_FILE` (default `.env`) and `SETUP_ENV_DOCS`
  (default `docs/TOKENS.md`) overrides, and reads answers from stdin so tests can pipe them.
- **Rationale**: Enables hermetic tests in a temp directory.

## Risks & Mitigations
- **Bash 3.2 incompatibility** — Mitigation: avoid associative arrays/`mapfile`; parse records with
  `while IFS='|' read`; test invocation under `/bin/bash`.
- **Doc/table drift** — Mitigation: docs generated by the same script; CI test diffs committed doc
  against a fresh `--emit-docs`.
- **Accidental clobber of populated keys** — Mitigation: line-by-line rewrite that only touches
  empty or absent keys; regression test on a rich fixture.
- **Value corruption from shell escaping** — Mitigation: `printf '%s'` for writes; `IFS=` and `read
  -r` for reads.
