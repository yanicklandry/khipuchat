# Research & Design Decisions: slack-all-workspaces

## Summary
- **Feature**: `slack-all-workspaces`
- **Discovery Scope**: Extension (existing Slack adapter) with a security-sensitive external integration, so light discovery was escalated on the auth, rate-limit, and desktop-import topics.
- **Key Findings**:
  - The current client already sends `Cookie: d=...` when `SLACK_COOKIE` is set, so a session-token backend is a contained change; the real gaps are error classification, scheduling, threads, and state.
  - The daemon never advances `sync_state` (`watch-lastsync` candidate), so every daemon cycle runs `runBackfill`, which message-events labels `backfill`. Without a fix, Slack messages would never reach triage as `live`. ~~The Slack adapter therefore records its own `sync_state` after each successful daemon cycle.~~ **Superseded by Phase 5 D1**: message-events `runAdapterCycle` writes `sync_state` when the adapter call resolves; Slack never writes it.
  - `conversations.list` with a user token returns every public channel in the workspace, joined or not. `users.conversations` returns only conversations the user is a member of, which matches slack-sync Req 2.1 and cuts request volume sharply.

## Research Log

### Existing Slack adapter and seams
- **Context**: Determine modification scope.
- **Sources Consulted**: `src/platforms/slack/client.ts`, `src/platforms/slack/sync.ts`, `tests/slack.test.ts`, `src/watch.ts`, `src/sync-runner.ts`, `src/account-registry.ts`, `src/db.ts`, `src/khipu.ts`, `src/khipu-sync-status.ts`, `scripts/setup-env.sh`.
- **Findings**:
  - `client.ts` (103 lines): fixed 1200 ms sleep before every request, one retry on 429, `conversations.list` over all types, `conversations.history`, `users.info` with an in-memory cache. Errors become `Error("Slack conversations.history error: <code>")`, unclassified.
  - `sync.ts` (136 lines): `mapChat` maps non-IM, non-MPIM to `'user'` (bug); `mapMessage` sets `is_sender: 0`, `reply_to_external_id: null`; `process.exit(1)` when the token is empty (kills the whole watch daemon). Incremental uses one platform-wide `oldest`.
  - `ChatType` is `'user' | 'group' | 'channel' | 'private'`. Other adapters use `'private'` for DMs and `'group'` for groups; `'channel'` is the natural fit for Slack channels.
  - `upsertChat` updates `type` and `name` on conflict, so a re-sync fixes wrong chat types without a migration.
  - `insertMessage` dedupes on `(external_id, chat_id)` and only upgrades `is_sender` from 0 to 1 on conflict, so re-reading old messages fixes the sent-by-me flag and nothing else.
  - The registry passes arbitrary string fields per account (`khipu.config.json` entry minus `name`), with `$VAR` resolution. Legacy mode synthesizes `default` from `SLACK_USER_TOKEN`/`SLACK_COOKIE`.
  - If `khipu.config.json` exists and is non-empty, the registry ignores legacy env for every platform. Writing that file from a login command could silently disable other platforms.
  - `docs/TOKENS.md` is generated by `scripts/setup-env.sh --emit-docs` from a catalog table, so the Slack documentation change is a catalog edit plus regeneration.
  - `watch.ts` `getIntervalMs(platform)` reads `WATCH_INTERVAL_<PLATFORM>_MS`, default 5 minutes. `pollCycle` picks `syncIncremental` only when `sync_state` has a value.
- **Implications**: rewrite the client on top of a transport; split `sync.ts` into mapping, cycle, and adapter; keep `hashStr`, `mapChat`, `mapMessage` exports for tests; add an optional adapter poll interval so the daemon can run Slack every minute without a global env change.

### Upstream contracts
- **cloud-deployment**: Slack's host requirement is `network`, so it runs on the server profile. `resolveDbPath` is used by entrypoints (the Slack one-shot `main()` already gets this change from cloud-deployment). `<NAME>_FILE` allowlist contains `SLACK_USER_TOKEN` only; per-account names and `SLACK_COOKIE` are missing. Its revalidation triggers list "changing the secret allowlist", so an additive change from this spec is expected and must update its env template and guide entry. cloud-deployment Req 13.6 already says Slack detection and re-auth belong to this spec.
- **message-events**: adapters keep calling `insertMessage`; origin is `live` only on the `syncIncremental` path, `backfill` otherwise. `runIngest(origin, fn)` from `src/ingest-context.ts` supports a nested inner scope. Historical reads inside a live cycle (new conversation import, chunked history) must run inside `runIngest('backfill', ...)` or they would emit `live` events for old messages.
- **presence-context**: no interaction.
- **notifier**: will need a durable, pollable signal. A table with a global sequence number lets it keep its own high-water mark without any callback from this spec.

### Slack Web API facts used
- **Sources Consulted**: Slack API method docs (`auth.test`, `users.conversations`, `conversations.history`, `conversations.replies`, `conversations.info`, `users.info`), Slack rate limit docs, Slack changelog 2025-05-29 (rate limit changes for non-Marketplace apps), community tooling notes on session tokens (slackdump).
- **Findings**:
  - Tiers: `users.conversations` Tier 3, `conversations.history` Tier 3, `conversations.replies` Tier 3, `conversations.info` Tier 3, `users.info` Tier 4, `conversations.list` Tier 2, `auth.test` special (generous). Tier 2 is about 20/min, Tier 3 about 50/min, Tier 4 about 100/min, per method per workspace per token.
  - Non-Marketplace distributed apps: `conversations.history` and `conversations.replies` limited to 1 request per minute and 15 objects per page; enforced on existing installs from 2026-03-03. An `xoxp` token from a self-made app installed in a workspace the developer does not own may fall in this bucket. Internal (same-workspace) apps are exempt.
  - Rate limited responses: HTTP 429 with `Retry-After` seconds and body `{ ok: false, error: "ratelimited" }`.
  - Session tokens (`xoxc-`) work only together with the `d` cookie (HttpOnly, so not readable from page JavaScript). The web client sends the token as a form field in a POST body; Bearer also works. The cookie value is usually URL-encoded already (contains `%2F`, `%3D`).
  - `localStorage.localConfig_v2` in the web client holds `teams`, an object keyed by team ID with `name`, `url`, `token` per signed-in workspace. One browser sign-in gives tokens for every signed-in workspace, sharing one `d` cookie.
  - Auth error codes: `invalid_auth`, `not_authed`, `token_revoked`, `token_expired`, `account_inactive` (credential dead); `enterprise_is_restricted`, `team_access_not_granted`, `org_login_required` (policy restriction); `channel_not_found`, `not_in_channel`, `missing_scope` (per-conversation or scope problem).
  - `conversations.history` returns newest first with `has_more` and cursor pagination; `oldest`/`latest` bound the window; thread parents carry `reply_count`, `latest_reply`, `thread_ts`. `thread_broadcast` replies appear both in history and in replies with the same `ts`.
  - `conversations.replies` returns the parent first then replies; `oldest` narrows to recent replies.
  - Enterprise Grid: org-level tokens may require `team_id` on conversation listing methods.
- **Implications**: per-method token-bucket limiter at about 80 percent of tier limits; classify errors into auth, restricted, conversation, rate-limited, transient; session backend uses POST form bodies so tokens never appear in URLs; optional `SLACK_TEAM_ID` field for Grid.

### Slack desktop import on macOS
- **Context**: Brief lists reading token and cookie from the desktop app as an optional helper.
- **Sources Consulted**: Chromium cookie storage on macOS (Safe Storage keychain item, `v10` prefix, PBKDF2-SHA1 with salt `saltysalt`, 1003 iterations, 16-byte key, AES-128-CBC, IV of 16 spaces; cookie DB meta version 24 and later prefixes the plaintext with a 32-byte SHA-256 of the host), Slack desktop data locations (direct download: `~/Library/Application Support/Slack`; App Store: `~/Library/Containers/com.tinyspeck.slackmacgap/Data/Library/Application Support/Slack`).
- **Findings**:
  - Tokens live in `Local Storage/leveldb/*.log` and `*.ldb`. `.log` is uncompressed; `.ldb` blocks may be Snappy-compressed, so a raw regex scan is best effort. Every candidate is validated with `auth.test`, which also maps it to its workspace.
  - Cookie `d` lives in the `Cookies` SQLite file, encrypted with the `Slack Safe Storage` keychain password, read via `security find-generic-password -w -s "Slack Safe Storage"` (prompts the user once).
  - `better-sqlite3-multiple-ciphers` opens the copied plain SQLite file read-only; `node:crypto` does PBKDF2 and AES. No new dependency.
- **Implications**: two small files (token scan, cookie decrypt), injected file system, keychain reader, and clock for tests; any failure falls back to manual steps (Req 2.13).

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| Per-conversation tiering inside the adapter (selected) | Daemon runs Slack every watched interval; the adapter plans which conversations are due | No change to daemon architecture; per-account state stays in the Slack boundary | Adapter grows a scheduler | Pure planner keeps it testable |
| One daemon timer per conversation | Daemon schedules each channel | Precise timing | Leaks Slack concepts into sync-watcher; hundreds of timers | Rejected |
| Realtime websocket from the web client | Push delivery | Seconds of latency | Undocumented protocol, higher detection risk, long-lived connection from a datacenter IP | Deferred stretch goal |
| `client.counts` change detection | One call lists channels with new activity | Very cheap | Undocumented, session-only, shape may change | Possible later optimization |
| Beeper Slack bridge | Use Beeper | Already works | Contradicts the goal of replacing Beeper | Rejected |

## Design Decisions

### Decision: Session backend as default, backend chosen by token prefix
- **Context**: Req 1. Non-admin access everywhere.
- **Alternatives Considered**:
  1. Explicit `SLACK_AUTH_MODE` field.
  2. Prefix detection (`xoxc-` session, `xoxp-` app).
- **Selected Approach**: prefix detection, no extra field. `xoxb-` and others are rejected as misconfigured.
- **Rationale**: the prefix is authoritative; one less setting to get wrong.
- **Trade-offs**: bot tokens unsupported (not needed for a personal archive).

### Decision: Generic persisted account health with a global sequence
- **Context**: Req 3; notifier must learn about re-auth without this spec calling it.
- **Alternatives Considered**:
  1. Emit a message-events row: wrong stream (events are new messages) and owned by message-events.
  2. In-process callback: lost on restart, couples to notifier.
  3. Table `account_health` keyed by (platform, account) with a sequence bumped on transitions.
- **Selected Approach**: option 3 in `src/account-health.ts`, platform-agnostic so other adapters can adopt it later.
- **Rationale**: durable, at-least-once for a polling consumer, no new process, no network.
- **Trade-offs**: consumers poll; transitions between two polls collapse to the latest state (acceptable: the notifier only needs the current state and the fact it changed).
- **Follow-up**: notifier records its last seen `seq`.

### Decision: Adapter records its own `sync_state` after a daemon cycle (SUPERSEDED by D1)
- **Status**: superseded by Phase 5 D1 (`.kiro/specs/phase5-cross-spec-decisions.md`): message-events `runAdapterCycle` writes `sync_state` on an ok outcome; the Slack adapter does not call `setPlatformLastSyncedAt`. Kept below for history only.
- **Context**: Req 7.8 and message-events origin rules; `watch.ts` never writes `sync_state`.
- **Selected Approach**: after a daemon cycle without auth failure, call `setPlatformLastSyncedAt('slack', account, now)`.
- **Rationale**: second and later cycles take the incremental path, so new messages are `live`. Idempotent once `watch-lastsync` lands.
- **Trade-offs**: duplicate write once the daemon fix lands (harmless).

### Decision: Historical reads wrapped in a nested backfill scope
- **Context**: Req 4.6, 5.5, 7.3, 7.4.
- **Selected Approach**: initial import of a new conversation, chunked history import, and forced re-reads run inside `runIngest('backfill', ...)` from message-events.
- **Rationale**: prevents old messages being reported as `live` during live cycles.
- **Trade-offs**: hard dependency on message-events' `ingest-context` for that task only.

### Decision: Members-only discovery via `users.conversations`
- **Context**: Req 4.1, 4.2; brief asks for list caching.
- **Selected Approach**: `users.conversations` with all four types, `exclude_archived=true`, cached in memory per adapter with a refresh interval; watched public channel IDs outside membership are read via `conversations.info` (Req 4.4).
- **Rationale**: avoids polling thousands of unjoined public channels.

### Decision: Thread tracking table with an activity window
- **Context**: Req 5. History with `oldest=cursor` does not return old parents whose threads got new replies.
- **Selected Approach**: every parent with `reply_count > 0` is recorded in `slack_threads` with Slack's `latest_reply` and the newest stored reply. A poll fetches replies when `latest_reply` moved, and re-checks the most recently active tracked threads (window 7 days, max 20 per poll) with `conversations.replies?oldest=<fetched>`.
- **Trade-offs**: replies to threads idle longer than the window are missed unless also posted to the channel or until the parent shows up again in a read. Documented as best effort.

### Decision: Login never creates `khipu.config.json`
- **Context**: Req 2.8, 2.9; the registry switches all platforms to file mode when the file exists.
- **Selected Approach**: update an existing file only; otherwise single workspace uses legacy vars, several workspaces print the entries with an explanation.
- **Rationale**: avoids silently disabling Telegram, Discord, and others configured through env.

### Synthesis outcomes
- **Generalization**: account health is generic (`platform`, `account`), Slack is its first writer. Session and app backends differ only in request encoding and expected limits, so one transport with a backend-specific request builder serves both.
- **Build vs adopt**: no Slack SDK (`@slack/web-api` does not support cookie-based session tokens cleanly and adds a dependency); Node `fetch`, `node:crypto`, `node:readline`, and the existing SQLite driver cover everything. No LevelDB library: best-effort scan plus validation is enough for an optional helper.
- **Simplification**: no realtime websocket; no persisted user-name cache (in-memory per run, DM chat names persisted in `chats`); degraded throttling counter kept in memory; no per-account daemon timers.

## Risks & Mitigations
- Session flagged as unusual access from a datacenter IP: conservative request spacing, no polling while unhealthy, documentation, clear re-auth path.
- Enterprise Grid rotation causes frequent `needs_reauth`: fast re-auth via `khipu slack login --account`, health visible in status.
- After long downtime, the gap between the stored position and now is read in a live cycle and reported as new messages (same as every other platform under message-events). triage-agent can filter by message age.
- Desktop import breaks with Slack or Chromium storage changes: best effort, always validated, manual fallback.
- First import of large workspaces is slow under Tier 3: chunked so watched conversations stay timely; status shows progress.
- Cookie and token leakage: POST bodies for session requests, redaction helper on every log and error path, tests asserting absence of secrets.
