## Usage Patterns
- Instantiate a `StringSession` (or `StoreSession` for Node filesystem persistence), pass it plus `apiId`/`apiHash` into `new TelegramClient(...)`, then call `client.start({...})` with async callbacks for `phoneNumber`, `password`, `phoneCode`, and `onError`.
- After first login, persist `client.session.save()` (a string) and reuse it in `new StringSession(savedString)` on subsequent runs to avoid re-authenticating.
- Use high-level convenience methods (`sendMessage`, `getDialogs`, `downloadMedia`) for common operations; drop to `client.invoke(new Api.SomeRequest({...}))` for anything not wrapped.
- In browser environments, bundle via the provided `webpack` config (`generate_webpack.js` / `NODE_ENV=production npx webpack`) since the package assumes Node built-ins (`fs`, `buffer`, `process`) are polyfilled; sessions fall back to `localStorage`.
- Wrap `invoke`/API calls in try/catch and inspect `errors` classes to handle flood waits and auth-required flows explicitly.

## Anti-Patterns
- Do not hardcode or commit `apiId`/`apiHash`, or the saved session string; treat both as secrets since a leaked session string grants full account access without re-authentication.
- Do not call `client.start()` repeatedly per-request; the client is meant to be instantiated once and reused/connected for the lifetime of the process.
- Do not assume `fs`-based `StoreSession` works in the browser; the `browser` field in package.json disables `fs`, so browser code must use `StringSession` or `localStorage`-backed storage.
- Do not bypass the queued/mutex-protected connection internals by manually managing sockets; the library relies on `async-mutex` internally for request ordering, so parallel raw invokes on a single client should go through `invoke()`, not custom transport code.
- Do not ignore `FLOOD_WAIT` errors by retrying immediately; respect the wait duration to avoid account restrictions.
