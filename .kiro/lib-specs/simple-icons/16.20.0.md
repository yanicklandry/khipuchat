## API Surface
Package `simple-icons@16.20.0` exposes four subpath entry points, each with dual ESM/CJS builds and TypeScript types:

- **`simple-icons`** (root) - the full icon set as named exports, one per brand, typed `SimpleIcon`. Icon identifiers follow a `si` + PascalCase-normalized-slug convention (e.g. `siGithub`, `si1and1`, `siCplusplus`, `siDotenv`). Also re-exports the `SimpleIcon` type.
- **`simple-icons/icons`** - identical named-export surface to root, isolated so bundlers can tree-shake without pulling in root-level extras.
- **`simple-icons/icons/*`** - direct per-icon file access (e.g. `simple-icons/icons/github`) for consumers who want to import a single icon module without touching the barrel file.
- **`simple-icons/sdk`** - programmatic helper functions (title/slug lookup, color/SVG-path utilities) for tooling that needs to work with icon metadata rather than fixed imports.
- **`simple-icons/icons.json`** - raw data file (title, slug, hex, path, source, license, aliases) as JSON, typed via `data/simple-icons.d.ts`.

Each `SimpleIcon` object exposes at minimum: `title`, `slug`, `svg` (raw markup), `path` (the `d` attribute), `hex` (brand color), `source`, and `guidelines`/`license` where applicable.

## Usage Patterns
- **Tree-shaken named import (recommended for apps/bundlers):** `import { siGithub } from 'simple-icons/icons'` pulls in only the requested icon(s); `sideEffects: false` in package.json guarantees bundlers can drop unused icons.
- **Single-icon deep import:** `import siGithub from 'simple-icons/icons/github'` when you want the smallest possible dependency graph or are avoiding barrel-file resolution cost.
- **Dynamic/data-driven rendering:** load `simple-icons/icons.json` and look up icons by slug at runtime (e.g. rendering an icon picker, mapping user-configured brand names to SVGs) instead of static imports.
- **SDK-assisted lookups:** use `simple-icons/sdk` when you need to resolve a brand name to its slug/title, validate hex colors, or manipulate SVG path data programmatically rather than hardcoding icon names.
- **SVG consumption:** consumers typically take `.path` and drop it into their own `<svg>` wrapper (setting size/viewBox themselves) rather than injecting `.svg` raw markup, to control styling/color via `fill="currentColor"` or the icon's `.hex`.
- Both ESM (`import`) and CJS (`require`) consumers are supported via the `exports` map; framework icon-component libraries (React/Vue/Svelte wrappers) commonly wrap this package rather than reimplementing icon data.

## Anti-Patterns
- **Don't import the entire root barrel (`import * as icons from 'simple-icons'`)** when only a handful of icons are needed — defeats tree-shaking and pulls hundreds of exports into the bundle graph even with `sideEffects: false`, since a namespace import forces the bundler to keep the whole module live.
- **Don't guess export names.** Icon names are not a simple `si` + title concatenation in all cases — numeric-leading and special-character brand names get normalized (e.g. `1&1` → `si1and1`, `C++` → `siCplusplus`, `.NET` → `siDotnet`). Always verify against the actual export or `icons.json` slug rather than hand-deriving the identifier.
- **Don't hardcode colors independent of `.hex`.** Brand colors are versioned data; icons occasionally update via brand-guideline changes. Pull `.hex` from the package rather than duplicating hard-coded hex strings, or updates will silently drift from what upstream ships.
- **Don't treat this as a runtime-agnostic package for old Node.** Despite `engines.node: >=0.12.18` in `package.json`, `devEngines.runtime` requires Node `>=22.18.0` — the stated broad engine range is legacy/inaccurate for actual compatibility; assume a modern Node/ESM-capable environment.
- **Don't rely on CommonJS `main`/`require` as the primary path going forward** — `type` isn't declared root-level as module but the `exports` map's `import`/`module` conditions are listed first, signaling ESM-first intent; `require` still works but is the secondary condition.
- **Don't assume icon presence across versions.** Icons are added/renamed/removed frequently between releases (brand rebrands, deprecations); pin the version and re-validate exports on upgrade rather than assuming a slug from an older version still exists.

## Constraints

Icon additions, removals, and renames happen on essentially every release — any code enumerating or hardcoding icon names must be re-verified against this exact version's export list.

- **Subpath-only access to per-icon files:** `./icons/*` is exported as a wildcard mapping to raw files, not individually typed per icon — types for individual deep imports come from the shared `index.d.ts` typings on the barrel, not a per-file `.d.ts`.
- **`sideEffects: false` requires a capable bundler** (webpack/rollup/esbuild/Vite) to actually realize the tree-shaking benefit; plain Node `require` of the whole package still loads all icon exports into memory.
