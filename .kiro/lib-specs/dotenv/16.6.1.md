## API Surface
**Core functions** (exported from `dotenv`):
- `config(options?: DotenvConfigOptions): DotenvConfigOutput` : reads `.env`, parses it, assigns to `process.env` (or a custom target), returns `{ parsed?: object, error?: Error }`.
- `configDotenv(options?: DotenvConfigOptions)` : lower-level equivalent of `config`, same signature/behavior.
- `parse<T>(src: string | Buffer): T` : parses `.env`-format content into a plain object without touching `process.env`.
- `populate(processEnv: object, parsed: object, options?: DotenvConfigOptions): void` : writes a parsed object into a target env-like object, honoring `override`/`debug`/`quiet`.
- `decrypt(encrypted: string, keyStr: string): string` : decrypts `.env.vault` ciphertext given a `DOTENV_KEY`.

**`DotenvConfigOptions`**: `path` (string | string[] | URL, default `./​.env`), `encoding` (default `utf8`), `quiet` (default `false`), `debug` (default `false`), `override` (default `false`), `processEnv` (default `process.env`), `DOTENV_KEY` (for vault decryption).

**Entry points**:
- `require('dotenv').config()` / `import 'dotenv/config'` (ESM side-effect import).
- `dotenv/config` preload: `node -r dotenv/config script.js` with `dotenv_config_<option>=value` CLI args or `DOTENV_CONFIG_<OPTION>` env vars.
- Subpath exports: `dotenv/lib/env-options`, `dotenv/lib/cli-options` (internal helpers for preload option parsing).

## Usage Patterns
- Call `require('dotenv').config()` (or `import 'dotenv/config'`) as early as possible, before any code reads `process.env`.
- Use `dotenv.parse(buffer)` when you want the parsed key/values without mutating `process.env` (e.g., custom plugin logic, feeding into `dotenv-expand`).
- Use the `path` option (array form) to layer multiple `.env` files, and `override: true` when a later file should win over already-set variables.
- Use preload (`-r dotenv/config`) to avoid needing a `require`/`import` call in app code, especially useful for entrypoint scripts or when you can't edit source easily.
- Pass a custom `processEnv` object instead of `process.env` when you want isolated configuration (e.g., per-request or per-tenant env objects) rather than mutating the global process.
- Check `result.error` after calling `config()` rather than assuming success, especially in scripts that must fail fast if `.env` is missing.
- In ESM projects, `import * as dotenv from 'dotenv'; dotenv.config()` must run and complete *before* importing modules that read `process.env` at import time (ES module hoisting loads all imports before top-level code runs) — either preload with `-r dotenv/config`, split into a separate bootstrap file, or use `import 'dotenv/config'` in the true entry file before other imports execute.

## Anti-Patterns
- Don't commit `.env` files to version control; they should hold only environment/deployment-specific secrets.
- Don't maintain multiple environment-specific `.env` files (`.env.test`, `.env.production`) as a "main config" strategy with this package alone — dotenv intentionally treats each deployment's environment as independent; use `dotenv-expand`/`dotenvx` if multi-environment file management is needed.
- Don't rely on `config()` to override existing `process.env` values by default — it will silently skip any key that's already set unless `override: true` is passed.
- Don't put unquoted values containing `#` in `.env` files — everything after an unquoted `#` is treated as a comment (breaking change since v15).
- Don't assume `import dotenv from 'dotenv'; dotenv.config()` in an ESM entry file configures env vars before other top-level imports execute — imports are hoisted and evaluated first, so modules relying on `process.env` at import time will see empty values; use `import * as dotenv` with careful ordering, preload, or a bootstrap module instead.
- Don't expect this package to work directly in browser/webpack bundles (e.g. React apps) — `fs`/`process` aren't available client-side; framework-specific env injection (e.g. `REACT_APP_` prefix in CRA) is required instead.
- Don't use `dotenv` for variable expansion (`${VAR}` interpolation) or command substitution — not supported natively; requires `dotenv-expand` or `dotenvx`.

## Constraints
- Requires Node.js `>=12`.
- Zero runtime dependencies.
- TypeScript types included (`lib/main.d.ts`), written against TS 3.0+ syntax.
- Multiline values (line breaks inside quoted strings) supported only from `v15.0.0` onward.
- `#`-starts-a-comment parsing behavior (unless value is quoted) is a breaking change introduced in `v15.0.0`.
- `quiet` option (suppress non-error output) is present in this version's types — a comparatively newer addition; older dotenv versions/docs don't reference it.
- Vault/encryption features (`DOTENV_KEY`, `decrypt()`, `.env.vault`) are supported for decrypting but the recommended path for encryption/multi-environment/sync workflows is the separate `dotenvx` CLI tool, not this library directly.
- `browser` field maps `fs` to `false`, signaling this package is not intended for direct browser bundling.
- No built-in variable expansion or command substitution; both require companion tools (`dotenv-expand`, `dotenvx`).
