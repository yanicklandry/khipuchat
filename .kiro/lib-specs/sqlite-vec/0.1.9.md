## API Surface
- `getLoadablePath(): string` — returns the absolute filesystem path to the platform-specific sqlite-vec extension binary (`.dylib`/`.so`/`.dll`), resolved via the matching `sqlite-vec-{platform}-{arch}` optional dependency.
- `load(db: Db): void` — loads the extension into an already-open database connection. `Db` is a minimal structural interface requiring only `loadExtension(file: string, entrypoint?: string): void`, so it's compatible with `better-sqlite3`, `node:sqlite`, and similar drivers without a hard dependency on any specific one.
- No other JS-level exports; all actual vector search functionality (virtual tables, functions like `vec_distance_cosine`, `vec_distance_l2`, `vec_distance_l1`, `vec0` virtual table module, etc.) is exposed through SQL once the extension is loaded, not through the JS API.
- Package ships both CJS (`index.cjs`) and ESM (`index.mjs`) builds plus TypeScript types (`index.d.ts`).

## Usage Patterns
- Standard load with `better-sqlite3`:
  ```js
  import Database from 'better-sqlite3';
  import * as sqliteVec from 'sqlite-vec';

  const db = new Database(':memory:');
  sqliteVec.load(db);
  ```
- Manual loading when `db.loadExtension` isn't directly compatible: call `getLoadablePath()` and pass the result to the driver's own extension-loading mechanism (e.g. `db.loadExtension(sqliteVec.getLoadablePath())`).
- After loading, use plain SQL to create vector tables and run queries:
  ```sql
  CREATE VIRTUAL TABLE vec_items USING vec0(embedding float[4]);
  INSERT INTO vec_items(rowid, embedding) VALUES (1, '[0.1, 0.2, 0.3, 0.4]');
  SELECT rowid, distance FROM vec_items WHERE embedding MATCH '[0.1,0.2,0.3,0.4]' ORDER BY distance LIMIT 5;
  ```
- Load the extension once per connection, immediately after opening the database and before running any vector-related SQL.
- The correct native binary is selected automatically at install time via the `optionalDependencies` matching the host OS/arch (darwin-x64, darwin-arm64, linux-x64, linux-arm64, windows-x64); no manual platform detection needed in application code.

## Anti-Patterns
- Don't call `load(db)` before extension loading is enabled on the underlying driver — some drivers (e.g. raw `node:sqlite` in older Node versions) require an `allowExtension`/similar flag at database-open time, or `loadExtension` will throw.
- Don't assume vector columns are typed/enforced beyond what `vec0` declares (e.g. `float[4]`) — inserting a vector of the wrong dimension will error at the SQL level, not the JS level; no JS-side validation exists.
- Don't treat this as a general-purpose ORM or query builder — it only loads a native extension; all querying is raw SQL.
- Don't bundle/ship only the JS package without its OS-specific optional dependency (e.g. via strict `--omit=optional` installs or aggressive dependency pruning) — `getLoadablePath()`/`load()` will fail to find the binary at runtime.
- Don't call `getLoadablePath()`/`load()` expecting a Promise — both are synchronous.
