## API Surface
Express 5.2.1 exports a default factory function `express()` that returns an `app` instance. Key surface:

- **`express()`** – creates an Express application.
- **`express.Router([options])`** – creates a modular, mountable route handler (built on `router@2.x`).
- **`express.static(root, [options])`** – serves static files (via `serve-static`/`send`).
- **`express.json([options])` / `express.urlencoded([options])` / `express.raw()` / `express.text()`** – built-in body-parsing middleware (wraps `body-parser@2.x`), replacing the old standalone `body-parser` requirement in app code.
- **`app.use([path], ...middleware)`** – mount middleware/routers.
- **`app.get/post/put/delete/patch/all(path, ...handlers)`** – route registration; route paths use `path-to-regexp` semantics as implemented by `router@2.x`.
- **`app.route(path)`** – chainable route builder.
- **`app.param(name, callback)`**.
- **`app.listen(...)`** – thin wrapper over `http.createServer(app).listen(...)`.
- **`app.set/get(name, value)`, `app.engine(ext, fn)`, `app.render(view, locals, callback)`** – view/config system.
- **`req` extensions**: `req.params`, `req.query` (now parsed with `qs@6.x` but no longer auto-includes `req.query` mutation guarantees from v4; getter-based in v5), `req.body`, `req.cookies` (only if `cookie-parser` used), `req.path`, `req.hostname`, `req.ip`/`req.ips`, `req.protocol`, `req.secure`, `req.xhr`, `req.accepts()`, `req.is()`, `req.range()`.
- **`res` extensions**: `res.send`, `res.json`, `res.jsonp`, `res.sendFile`, `res.sendStatus`, `res.download`, `res.redirect`, `res.render`, `res.cookie`/`res.clearCookie`, `res.set`/`res.get`, `res.status`, `res.type`, `res.format`, `res.attachment`, `res.append`, `res.location`, `res.vary`.
- Error handling middleware signature `(err, req, res, next)`; async handlers may now `throw`/reject and Express 5 automatically forwards rejected promises to `next(err)` (new in v5, no longer requires manual `try/catch` + `next(err)`).

## Usage Patterns
- ESM or CJS both supported; README now shows `import express from 'express'` as the canonical example (package still supports `require('express')`).
- Compose apps with `express.Router()` per resource/domain and mount via `app.use('/prefix', router)`.
- Use built-in `express.json()`/`express.urlencoded()` instead of pulling in `body-parser` directly for standard JSON/form parsing.
- Serve static assets with `express.static('public')`, layering multiple static roots via multiple `app.use(express.static(...))` calls.
- Use `app.set('view engine', ...)` with a template engine (e.g. `ejs`, `hbs`) for server-rendered views; Express does not bundle a default engine.
- Centralize error handling in a single terminal error-handling middleware (`(err, req, res, next)`) placed after all routes; since v5 supports async rejection forwarding, async route handlers can simply `throw`.
- Use `express-generator` (installed separately, matching major version per README: `express-generator@4`) to scaffold new apps rather than hand-building boilerplate.
- Use `app.param()` for shared per-parameter preloading logic (e.g., loading a resource by `:id` once per matching route).
- Trust proxy configuration (`app.set('trust proxy', ...)`) via `proxy-addr` when behind reverse proxies, for correct `req.ip`/`req.protocol`.

## Anti-Patterns
- Do not manually `try/catch` + call `next(err)` for every async handler purely to forward promise rejections — Express 5 does this automatically; retain try/catch only for logic needing local recovery, not for propagation.
- Do not assume Express 4 path-matching behavior: wildcard/optional-parameter syntax changed under `router@2.x`/`path-to-regexp` in v5 (e.g., bare `*` splat and some regex-like patterns behave differently or throw); avoid copy-pasting v4-era route patterns without verifying them against v5's routing engine.
- Do not treat `req.query`/`req.params` as freely reassignable objects in all cases — v5 tightened some of these to be getter-derived; avoid patterns that mutate the underlying property descriptor rather than the object contents.
- Do not add third-party `body-parser` as a direct dependency purely for `json()`/`urlencoded()` — use the built-in `express.json()`/`express.urlencoded()` to avoid version drift against the internal `body-parser@2.x` Express already depends on.
- Do not use Express on Node < 18 — the `engines.node` field enforces `>= 18`; do not target this package for legacy Node runtimes.
- Do not deep-require internal implementation files (`express/lib/...`) as a substitute for public API — the public surface is `index.js` + documented `app`/`req`/`res`/`router` methods only per the package's `files` field.
- Do not skip reading the official v4→v5 migration guide before upgrading an existing v4 app — breaking changes span routing, removed deprecated methods, and dependency majors (`send`, `serve-static`, `qs`, `router`, `mime-types` were all bumped to new majors).

## Constraints
- **Node.js `>= 18` required** (`engines.node`).
- Major-version-bumped dependencies vs. Express 4: `router@2.x`, `send@1.x`, `serve-static@2.x`, `body-parser@2.x`, `qs@6.14+`, `mime-types@3.x`, `type-is@2.x`, `accepts@2.x`, `cookie@0.7.x`, `merge-descriptors@2.x`, `content-disposition@1.x`, `fresh@2.x`, `http-errors@2.x`, `finalhandler@2.x` — these dictate v5's routing, content-negotiation, and static-file behavior and are not backward-compatible drop-ins with their v4-era counterparts.
- Router matching is delegated entirely to `router@2.x`; any code relying on Express 4's bundled routing quirks must be revalidated.
- `express-generator` is a separate package with its own major version (pin `@4` per README) and is not bundled with `express` itself.
- View engine support is not bundled: template engines (14+ supported via `@ladjs/consolidate` per README) must be installed and wired explicitly via `app.engine()`/`app.set('view engine', ...)`.
- No built-in session, auth, or logging middleware — session handling (`express-session`, `cookie-session`), cookies (`cookie-parser`), logging (`morgan`) are devDependencies for the test suite only, not shipped runtime capabilities of the `express` package itself.
