## API Surface
- **Default export** — `expressBasicAuth(options: BasicAuthMiddlewareOptions): RequestHandler`. Callable factory that returns an Express middleware function; imported via `const basicAuth = require('express-basic-auth')` or `import * as basicAuth from 'express-basic-auth'` (uses `export =`, no default/named ESM export).
- **`expressBasicAuth.safeCompare(userInput: string, secret: string): boolean`** — timing-safe string comparison. Exported as a namespace member for use inside custom authorizers.
- **Options object** (union of three shapes, discriminated by which keys are present):
  - `IUsersOptions`: `{ users: { [username: string]: string } }` — static credential map.
  - `IAuthorizerOptions`: `{ authorizer: (username, password) => boolean, authorizeAsync?: false }` — synchronous custom check.
  - `IAsyncAuthorizerOptions`: `{ authorizer: (username, password, callback: (err, authed?) => void) => void, authorizeAsync: true }` — async custom check via Node-style callback.
  - Shared `IBaseOptions` fields available on all three: `challenge?: boolean` (default `false`, adds `WWW-Authenticate` header), `realm?: string | (req) => string`, `unauthorizedResponse?: any | (req) => any` (string used as-is, else sent as JSON).
- **Request augmentation** — sets `req.auth = { user, password }` on any request that presents *any* basic-auth header, whether or not it's valid. TypeScript type for this is `IBasicAuthedRequest` (extends Express `Request`), used via manual cast/downcast in handler signatures, not automatic global augmentation.
- Depends on `basic-auth@^2.0.1` for header parsing; peer-installs against `express@^4.16.x` (devDependency only, not a hard runtime peerDependency in package.json).

## Usage Patterns
- Mount as middleware before protected routes: `app.use(basicAuth({ users: { admin: 'supersecret' } }))`.
- Static multi-user credential maps for simple deployments (internal tools, staging environments).
- Custom `authorizer` for DB/external lookups; **must** use `safeCompare` (with user input as the *first* argument) plus bitwise `&`/`|` instead of `&&`/`||` to avoid short-circuit timing leaks.
- Async authorizer (`authorizeAsync: true`) for lookups requiring I/O (DB queries, remote auth services), signaled via Node-style `(err, authed)` callback.
- `challenge: true` + `realm` to trigger the browser's native basic-auth popup instead of a bare 401.
- Custom `unauthorizedResponse` function to shape 401 bodies (e.g., echoing back which credentials were rejected via `req.auth`), useful for API clients that need machine-readable error responses.
- Route-scoped mounting (`app.use(basicAuth(...), specificHandler)`) to protect only a subset of routes rather than the whole app.
- In TypeScript, downcast `req` to `basicAuth.IBasicAuthedRequest` in downstream handlers to access `req.auth` without a type error.

## Anti-Patterns
- Comparing credentials with `===`/`==` or `&&`/`||` inside a custom `authorizer` — enables timing attacks; always use `safeCompare` with bitwise operators.
- Passing `userInput` and `secret` to `safeCompare` in the wrong order — runtime depends only on the first argument, so swapping order leaks timing info about the secret instead of protecting it.
- Treating basic auth as sufficient security on its own for sensitive systems — credentials are sent base64-encoded (not encrypted) on every request; **must** be paired with HTTPS/TLS, since this middleware does nothing to protect transport.
- Assuming `req.auth` implies a validated user — it's populated whenever *any* basic-auth header is present, valid or not; only the middleware's pass/block decision (not the mere presence of `req.auth`) indicates authorization.
- Mixing `authorizeAsync: true` with a synchronous authorizer function (or vice versa) — the callback signature must match the declared mode or the middleware will hang or throw.
- Relying on TypeScript to infer synchronous authorizer argument types — due to a TS limitation noted in the README, sync authorizer params (`username`, `password`) are not inferred and must be typed explicitly; async authorizers infer correctly.
- Storing plaintext static passwords in source-controlled `users` maps for production use — fine for examples/local dev, not a substitute for a real credential store.

## Constraints
- Requires `express` as a runtime peer (only listed under `devDependencies`, `^4.16.4`) and `@types/express ^4.16.0` for TypeScript consumers — not compatible out-of-the-box declarations-wise with Express 5 given this package's era.
- TypeScript declarations were authored/tested against TypeScript `^2.9.2`; modern TS versions generally still work but the documented sync-authorizer inference gap is a known, unfixed limitation from that generation of the type system.
- No built-in support for hashed/salted password storage, rate limiting, or lockout — purely a credential-compare/parse middleware; anything beyond static or custom-authorizer comparison must be built by the consumer.
- CommonJS module (`export =` / `module.exports`), so ESM default-import interop requires `esModuleInterop`/`allowSyntheticDefaultImports` or the `import * as basicAuth` form shown in docs.
- Single stable options shape per call — cannot mix `users` and `authorizer` in the same options object (the type is a discriminated union, not a merge).
- Depends on `basic-auth@^2.0.1` for `Authorization` header parsing; any parsing quirks/limitations (e.g., malformed header handling) are inherited from that package, not reimplemented here.
