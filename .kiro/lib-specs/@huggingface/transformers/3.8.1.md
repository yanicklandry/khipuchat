## API Surface
The package exports everything from `src/transformers.js` as ESM (also usable via CJS/Node build and browser `<script type="module">`/CDN). Key exports:

- **`pipeline(task, model?, options?)`** — async factory returning a task-specific pipeline instance (e.g. `TextClassificationPipeline`, `AutomaticSpeechRecognitionPipeline`, `ImageSegmentationPipeline`, etc.). The primary high-level entry point; calling the returned pipeline with input (and optional per-call options) returns a `Promise` of results.
- **`env`** — global runtime configuration singleton (`env.localModelPath`, `env.allowRemoteModels`, `env.backends.onnx.wasm.wasmPaths`, cache directories, etc.).
- **Model classes** (`models.js`) — `AutoModel`, `AutoModelForCausalLM`, `AutoModelForSeq2SeqLM`, `AutoModelForImageClassification`, task-specific `PreTrainedModel` subclasses, all with static `.from_pretrained(modelId, options)`.
- **Tokenizers** (`tokenizers.js`) — `AutoTokenizer`, `PreTrainedTokenizer`, with `.from_pretrained()` and `encode`/`decode`/callable interfaces.
- **Configs** (`configs.js`) — `AutoConfig`, `PretrainedConfig`.
- **Processors** — `FeatureExtractor`, `ImageProcessor`, `Processor` base classes plus `AutoFeatureExtractor`/`AutoImageProcessor`/`AutoProcessor` factories, and modality utilities (`utils/audio.js`, `utils/image.js`, `utils/video.js`).
- **Tensor utilities** (`utils/tensor.js`, `utils/maths.js`) — a `Tensor` class and math helpers used across pre/post-processing.
- **Generation utilities** (`generation/`) — `streamers.js` (e.g. `TextStreamer` for token-by-token output), `stopping_criteria.js`, `logits_process.js` for customizing `.generate()` behavior.
- Type declarations ship in `types/transformers.d.ts`, so TypeScript consumers get full typing without `@types` packages. Notable exported types: `PretrainedModelOptions`, `PretrainedProcessorOptions`, `DataType`, `DeviceType`.
- Exports are conditional per environment: `exports.node.import/require` map to `dist/transformers.node.mjs`/`.cjs` (uses `onnxruntime-node` + `sharp`), while the `default` condition (browser/bundler) maps to `dist/transformers.web.js` (uses `onnxruntime-web`, WASM/WebGPU backends). A minified UMD-style build is available via `jsdelivr`/`unpkg` (`dist/transformers.min.js`) for `<script>` tag / CDN usage without a bundler.

## Usage Patterns
- **Pipeline-first for common tasks**: `const pipe = await pipeline('sentiment-analysis'); const out = await pipe('text');` — mirrors the Python `transformers` pipeline API almost 1:1, making porting Python code straightforward.
- **Explicit model selection**: pass a Hugging Face Hub model id/path as the second argument to `pipeline()` to override the task's default model, e.g. `pipeline('sentiment-analysis', 'Xenova/bert-base-multilingual-uncased-sentiment')`.
- **Device/backend selection**: pass `{ device: 'webgpu' }` (or `'wasm'`/`'cpu'`/etc.) to run on GPU via WebGPU instead of the CPU/WASM default.
- **Quantization/dtype selection**: pass `{ dtype: 'q4' | 'q8' | 'fp16' | 'fp32' }` to control precision/size tradeoffs; `q8` is the default on WASM and `fp32` on WebGPU. Lower-bit quantized models reduce bandwidth/memory in browser contexts.
- **Global config via `env`** before creating pipelines/models: set `env.localModelPath` to serve self-hosted models, `env.allowRemoteModels = false` to force offline/local-only operation, and `env.backends.onnx.wasm.wasmPaths` to self-host WASM binaries instead of using the default CDN.
- **Model conversion workflow**: models must be converted to ONNX (typically pre-quantized) before use, via the Python `scripts/convert.py` (built on 🤗 Optimum): `python -m scripts.convert --quantize --model_id <model>`, producing `config.json`, `tokenizer.json`, `tokenizer_config.json`, and `onnx/model[_quantized].onnx`. Not every PyTorch/TF/JAX architecture is exportable; check Optimum's supported-architecture list first.
- **Dual environment usage**: same import statement (`import { pipeline } from '@huggingface/transformers'`) works in Node (server-side inference, using `onnxruntime-node`/`sharp`) and in the browser (client-side, using `onnxruntime-web`), or directly via CDN with no build step — pick the backend implicitly via the package's conditional exports.
- **Streaming generation**: for text-generation-style tasks, use `TextStreamer` from `generation/streamers.js` to receive incremental token output rather than waiting for the full result.
- **Task ID aliases**: some tasks accept multiple string IDs (e.g. `'text-classification'`/`'sentiment-analysis'`, `'token-classification'`/`'ner'`, `'text-to-speech'`/`'text-to-audio'`) — pick whichever reads more naturally in context.

## Anti-Patterns
- Don't treat `pipeline()` or model/tokenizer `.from_pretrained()` calls as synchronous — they are async (they fetch/cache model weights and initialize an ONNX Runtime session) and must be awaited; forgetting `await` yields a `Promise` object being used as a callable/model, causing silent failures.
- Don't assume every Hugging Face Hub model works out of the box — only models with an ONNX export (either pre-converted and tagged `transformers.js` on the Hub, or converted locally via `scripts/convert.py`) are usable; PyTorch/TF checkpoints without an ONNX export will fail to load.
- Don't request `device: 'webgpu'` unconditionally in production browser code without a fallback — WebGPU is still experimental/inconsistently supported across browsers and may throw or behave unpredictably; feature-detect or catch errors and fall back to WASM/CPU.
- Don't ship unquantized (`fp32`) models to browser clients by default for bandwidth-sensitive apps — prefer explicit `dtype` selection (`q8`/`q4`/`fp16`) appropriate to the target model and environment; the "best" default varies per architecture, so don't assume one dtype works everywhere.
- Don't mix the Node-specific build assumptions with browser code or vice versa — the package resolves different entry points (`transformers.node.mjs/cjs` vs `transformers.web.js`) via conditional exports; manually deep-importing `dist/transformers.node.mjs` in a browser bundle (or forcing Node's `onnxruntime-node`/`sharp` deps into a browser build) will break.
- Don't rely on this library for tasks marked unsupported in the task table (e.g. table-question-answering, mask-generation, text-to-image, visual-question-answering, audio-to-audio, video-classification, tabular tasks) — these will not have a corresponding `*Pipeline` class even though the Python library may support them.
- Don't hardcode `env.allowRemoteModels = false` while also expecting the library to transparently fall back to the Hub — with remote models disabled, `localModelPath` must actually contain the required model files or loading will fail outright.
- Don't assume `types` resolve automatically if hand-rolling module resolution/bundler config — the `exports` map ties `types` to each conditional export (node import/require vs default), so unusual bundler setups that ignore `exports` conditions may fail to pick up `types/transformers.d.ts`.

## Constraints
- Requires ESM (`"type": "module"`); CJS consumers in Node must use the `require` conditional export (`dist/transformers.node.cjs`), not the browser bundle.
- Node-side native dependencies: `onnxruntime-node@1.21.0` and `sharp@^0.34.1` — both are native/prebuilt-binary packages, so Node deployment targets (e.g. serverless/edge runtimes, certain Docker base images) must be compatible with their platform binaries; environments without native module support (some edge runtimes) cannot use the Node build.
- Browser/web build depends on `onnxruntime-web@1.22.0-dev.20250409-89f8206ba4` — a dev/pinned prerelease version, meaning WebGPU/WASM backend behavior may shift between transformers.js releases as this pinned dependency updates.
- WebGPU support is explicitly experimental at this version; expect browser-dependent bugs and file issues against the project rather than assuming a stable, cross-browser GPU path.
- Template/prompt formatting (e.g. chat templates) depends on `@huggingface/jinja@^0.5.3`; any Jinja templating limitations of that pinned range apply here too.
- Default model/WASM asset loading points at a CDN (jsDelivr, per the `jsdelivr`/`unpkg` fields) — fully offline/air-gapped use requires explicitly configuring `env.localModelPath`, `env.allowRemoteModels = false`, and `env.backends.onnx.wasm.wasmPaths` to self-hosted assets.
- TypeScript support requires TS tooling compatible with the shipped `.d.ts` and the package's `exports`-map-based type resolution (generated via `tsc --build`); very old TS/bundler resolution modes (non-`node16`/`bundler`) may not honor the conditional `types` correctly.
- Version `3.8.1` is part of the actively evolving 3.x line; supported architectures/tasks (per the README's model/task tables) change between minor versions, so pin the version and re-check supported-task tables before upgrading.
