## API Surface
**Top-level module (`Tesseract`, default export):**
- `createWorker(langs?, oem?, options?, config?) => Promise<Worker>` - primary entry point; creates and initializes a ready-to-use worker in one call
- `createScheduler() => Scheduler` - creates a job queue that distributes work across multiple workers
- `recognize(image, langs?, options?) => Promise<RecognizeResult>` - one-shot convenience wrapper (creates/tears down an internal worker per call)
- `detect(image, options?) => Promise<DetectResult>` - one-shot script/orientation detection
- `setLogging(boolean) => void`

**`Worker` instance methods:**
- `recognize(image, options?, outputFormats?, jobId?) => Promise<RecognizeResult>` - core OCR call, returns a `Page` object (`text`, `words`, `lines`, `blocks`, `hocr`, `tsv`, `pdf`, etc. depending on requested `OutputFormats`)
- `detect(image, jobId?) => Promise<DetectResult>` - orientation/script detection
- `setParameters(params) => Promise<ConfigResult>` - tune Tesseract engine params (e.g. `tessedit_pageseg_mode`, char whitelist/blacklist) between recognitions
- `reinitialize(langs?, oem?, config?) => Promise<ConfigResult>` - swap languages/OEM on an existing worker (cheaper than creating a new one)
- `load/writeText/readText/removeText/FS(...)` - low-level virtual filesystem access for the underlying WASM engine
- `getPDF(title?, textonly?) => Promise<GetPDFResult>` - legacy PDF export (v4+ prefers `pdf` in `OutputFormats`)
- `terminate() => Promise<ConfigResult>` - releases the WASM worker/thread; must be called explicitly

**`Scheduler`:**
- `addWorker(worker) => string`, `addJob('recognize'|'detect', ...args) => Promise<...>`, `getQueueLen()`, `getNumWorkers()`, `terminate()`

**Data model:** `ImageLike` accepts `string` (path/URL/base64), DOM elements (`HTMLImageElement`, `HTMLCanvasElement`, `HTMLVideoElement`, `OffscreenCanvas`, `CanvasRenderingContext2D`), `File`/`Blob`/`ImageData`, or Node `Buffer`. Recognition results expose a hierarchical `Page > Block > Paragraph > Line > Word > Symbol` tree with `bbox`, `confidence`, `baseline`, and font metadata at each level.

## Usage Patterns
- Standard single-image flow: `const worker = await createWorker('eng'); const { data } = await worker.recognize(image); await worker.terminate();`
- **Reuse one worker across multiple images** rather than calling `recognize()` (top-level) or `createWorker`/`terminate` repeatedly - worker creation loads WASM + language data and is expensive.
- Set language(s) and OEM directly in `createWorker(langs, oem, options)` rather than separate init calls (this changed from v2's `load()`/`loadLanguage()`/`initialize()` sequence).
- Use `worker.setParameters({ tessedit_pageseg_mode: PSM.SINGLE_BLOCK })` between calls to retune segmentation without recreating the worker.
- Use `worker.reinitialize(newLangs)` when switching languages mid-session instead of terminating and recreating the worker.
- Use `createScheduler()` + multiple `createWorker()` instances added via `scheduler.addWorker()` for parallel throughput (e.g. batch OCR jobs, Node.js server processing multiple requests).
- Pass `logger: (m) => ...` in `WorkerOptions` to surface progress (`status`, `progress`) for long-running recognitions, particularly relevant since UX often needs progress bars for OCR.
- Request only the output formats needed via the `OutputFormats` param (`text`, `hocr`, `tsv`, `blocks`, etc.) - each enabled format adds processing/memory cost.
- In Node.js, `ImageLike` can be a file path string or `Buffer` directly; no DOM canvas needed.

## Anti-Patterns
- **Don't create a new worker per image.** Repeated `createWorker`/`terminate` (or repeated top-level `recognize()`) reloads WASM binaries and language traineddata every time - a major performance anti-pattern explicitly called out in the docs.
- **Don't forget to call `worker.terminate()`.** Workers hold WASM memory/threads that won't be reclaimed otherwise, causing memory leaks in long-running processes (servers, Electron apps).
- **Don't call `worker.load()`, `worker.loadLanguage()`, or `worker.initialize()` in v5** - these are now no-ops left only for backward compatibility; passing langs/OEM to `createWorker` is the only supported path. Code carried over from v2 that still relies on init sequencing will silently do nothing.
- **Don't call `getPDF()` when `pdf` output via `recognize(..., { pdf: true })` suffices** - `getPDF` is a legacy path; the v4+ `OutputFormats.pdf` flag on `recognize` is preferred.
- **Don't request all `OutputFormats` (hocr/tsv/box/unlv/osd/images) by default** - each enabled format increases processing time and result payload size; request only what's consumed.
- **Don't assume `detect()`'s return type is well-typed** - the top-level `Tesseract.detect` is typed `any` in the `.d.ts`; only `Worker.detect`/`Scheduler`'s `DetectResult` is properly typed.
- **Don't block a single worker with many concurrent `recognize()` calls expecting parallelism** - a single `Worker` processes jobs serially; use `Scheduler` with multiple workers for true parallel throughput.

## Constraints
- **Node.js >= 14** required (Node 10/12 support dropped as of v3). Node 18 is the officially tested modern target.
- **Breaking change from v4 to v5**: `createWorker` signature changed to accept `(langs, oem, options, config)` directly; language/OEM must be set at creation time (or via `reinitialize`), not via separate `initialize`/`loadLanguage` calls.
- **Breaking change from v3 to v4**: `createWorker` became async (returns a `Promise<Worker>`); `getPDF()` function was replaced conceptually by the `pdf` recognize option (though `getPDF` remains available).
- v5 significantly reduces default file sizes (54% smaller for English, 73% for Chinese/CJK) and memory usage versus v4, and is compatible with iOS 17 default settings - relevant if targeting Safari/iOS webviews.
- Depends on `tesseract.js-core@^5.1.1` (the WASM engine binding) - core and wrapper versions should stay in lockstep.
- Browser bundling has a dedicated `browser` field remapping `src/worker/node/index.js` to `src/worker/browser/index.js`; webpack/bundler configuration matters for correct worker resolution (Web Worker in browser vs. worker_threads/child_process in Node).
- `imageType` (used by `worker.getImage`) is a `const enum`, meaning consuming TypeScript projects must have compatible `isolatedModules`/`preserveConstEnums` settings or transpilation can break.
- No native SIMD/ASM.js fallback below v3's SIMD-enabled build; very old Tesseract.js-core versions (<3.0.0) are unsupported.
- `WorkerParams` has an index signature (`[propName: string]: any`), so parameter names/values are not compile-time validated - typos in Tesseract engine parameter names fail silently at runtime rather than at compile time.
